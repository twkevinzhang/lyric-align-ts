# 三曲歌曲對齊：10 秒效能目標

## 目的與已確認驗收
在目前 Chrome CPU/WASM 歌曲對齊流程持續改善效能，保留可查證的三曲測量與決策報告。每首獨立要求 totalSeconds <= 10；計時包括模型初始化、完整歌曲對齊、RPC，不包括音檔解碼、模型傳入瀏覽器、編譯與評分。不得把原本計時範圍內的計算移到計時外來達標。

三曲分別為 TestSet/amazing_grace、SUNEO-ISM、春泥棒，音檔皆為 256k-16kHz-單聲道.wav。歌詞依次為 Original.txt、e1ZMmRlsaaU.txt、source.srt，標準答案依次為 Original.srt、e1ZMmRlsaaU.srt、source.srt，根目錄 C:/Users/DragonXwin10/Downloads/audio/TestSet。

每個參考 SRT 區塊為一句。每首可排除最多 floor(句數 * 0.1) 句；缺漏、無效或配對失敗先占此額度，其餘額度排除句首絕對誤差最大的句子。保留句子全部必須有效，且句首平均絕對誤差 <= 1 秒。報告列出排除句、保留平均誤差、各句誤差與缺漏。句尾可報告，不影響驗收。三首必須各自通過，不合併平均。

標準時間只供評分，禁止用於推論、裁切、調參的歌曲專屬時間修正或回填；春泥棒輸入 SRT 僅抽取文字。禁止重用前次對齊輸出假裝新推論。

## 允許改動與工程師決策
使用者允許調整推論參數及內部演算法。工程師決策：先沿用既有多語 small Q5_1 與 CPU/WASM 路線，量測 encoder、decoder、RPC、初始化和 DTW，依瓶頸選擇參數、批次解碼、資料傳輸或運算核心改進。評估替代內部演算法時仍須全曲重新推論，揭露模型與參數。此工作不涵蓋 UI 重設、雲端部署、GPU 路線或改用原生後端冒充 WASM 達標。

## 迭代與交付
先修正驗收工具並測試邊界，再重測三曲建立可重現基線；每輪記錄程式版本/變更、輸入及模型雜湊、參數、執行緒、實際時間、句首品質、是否採用與下一步。先做具體瓶頸假設，再改一類因素測試；失敗也記錄原因。候選全部通過後，以相同環境每首重跑三次，每次均需通過時間與品質。維持使用者既有多工環境，不停止他人程序。

最新整合報告說明基線、各實驗結果、目前最佳候選與下一步；原始測量放 .local/whisper-poc 下，報告不得把不同設定的舊數字當作當前結果。只保留一份持續更新的設計與一份整合報告，歷史文字版本由 Git 保存。尚未達標時明確標示未達標並繼續可驗證的改進，不承諾一定能在 CPU/WASM 下達成 10 秒。

執行流程：
輸入音檔與歌詞 -> 解碼/準備（不計時）
  -> [初始化 -> 分段 encoder -> 歌詞對齊/decoder/DTW/RPC]（<=10 秒）
  -> 標準 SRT 評分 -> 排除 <=10% -> 保留 MAE <=1 秒
  -> 更新整合報告 -> 決定下一輪 -> 再測三曲

只按需啟動測試服務，記錄 command/cwd/port/session 並驗證連線。交付前預設停止本次啟動的服務；使用者明確要求保留時才保留。是否提交另依 make-git 技能處理，不為保存設計自行提交。
