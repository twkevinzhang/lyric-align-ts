# lyric-align-ts

將 [lyric-align](https://github.com/ijuinryukichi/lyric-align) 的歌詞對齊流程移植至瀏覽器的技術驗證。目前程式位於 `spike/`，是可丟棄原型，尚非正式函式庫。

## 執行

需要 Node.js 24 與 npm，優先使用桌面 Chrome 和支援 WebGPU 的顯示卡。

```sh
cd spike
npm ci
npm run dev
```

開啟 `http://127.0.0.1:5173/`，選擇音檔、載入模型、開始辨識。初次使用會從 Hugging Face 下載模型；音訊與歌詞不會傳至辨識服務。開發伺服器只負責提供本機檔案，沒有後端推論。

## 目前範圍

- Transformers.js 4.3.1，WebGPU，encoder 與 decoder 均使用 `q4`，不自動切換至其他精度或 CPU。
- 使用固定 revision 的 Whisper tiny／base／small、多語與英文專用候選，以及 Wav2Vec2 CTC q4 對照模型，實際 ID 與 revision 見 `spike/app/lib/protocol.ts`。模型均以 `device: webgpu`、`dtype: q4` 載入。
- 英文辨識，30 秒區塊、左右各 5 秒重疊，可測開頭 30 秒或整首音檔。
- 保留原始詞級時間戳，列出缺失、倒序、零長度、重疊及重複項目。
- 依停頓與段落長度重建 segments，再執行初步行級歌詞對齊。重建規則為實驗性轉接，並非 Whisper 原生段落。
- 預設辨識可將同一批生成 token 額外解碼成原生段落，保留重疊合併前各視窗的 token、文字與 token 時間；依賴固定 4.3.1 的 tokenizer 私有 API。預設保留原始時間，只有明確選擇「時間修正候選」才啟用可選實驗。
- 支援人工 SRT 對應的行起點評分；逐字卡拉 OK 時間與完整字幕格式匯出尚未移植。

## 本機測試素材與報告

`.local/` 全部由 Git 忽略。音檔、完整歌詞、辨識文字、下載來源資料與原始診斷報告都留在此目錄，不隨公開 repository 發布。

本機素材可放在 `.local/test-media/amazing_grace/amazing_grace.m4a` 與同目錄的 `amazing_grace.txt`。開發模式提供「載入本機 Amazing Grace」按鈕；production build 不包含這些素材或本機讀檔路由。也可以直接在頁面選擇音檔與貼上歌詞。

人工 SRT 位於同目錄的 `amazing_grace.en.srt`。本輪已逐項核對歌詞行與字幕段落的對應，存於本機 `.local/results/reference-map.json`；開發頁會讀取此對應資料。評分要求音檔 SHA-256 與歌詞行相符，且只針對整首辨識結果。參考資料不會傳給辨識 worker。更新素材後必須重新核對對應，不以舊報告代表新音檔。

「匯出本機診斷 JSON」會下載模型設定、音檔雜湊、原始辨識結果、對齊結果、錯誤與 JS heap 樣本。報告含音訊衍生文字及歌詞，應留在本機。頁面重新整理會清除尚未匯出的結果。

「無時間戳辨識控制組」及「原生段落辨識控制組」使用相同已載入的 q4 模型與音訊區間，分別設定 `return_timestamps: false`／`true`，兩者都不要求 `return_token_timestamps`。結果另存於匯出報告的 `textControls`，每筆附實際模式、模型與音檔雜湊，不混入詞級評分。原本的「開始辨識」仍為詞級時間戳模式。

改善實驗另存於 `experimentRuns`，每筆記錄實際生成參數及時間修正模式。五組 Whisper 對照涵蓋生成上限、四 token n-gram 抑制與 15／30 秒切片。歌詞提示使用 Whisper 的 previous-text 區域，僅把歌詞文字傳入 worker，不傳人工 SRT；提示對照關閉 n-gram 抑制，避免內建抑制器把提示中的正確歌詞也列為禁止生成的片段。

CTC 強制對齊為獨立、可丟棄實驗：20 秒分窗、2 秒重疊，保留中間聲學 frame，以 Viterbi 對齊提供的英文歌詞。其 `text` 與詞數來自提供歌詞，`raw_asr_text` 才是獨立聲學辨識輸出；不能將提供文字的 WER 當作辨識品質。CTC 輸出不會自動成為預設歌詞對齊結果。

「改善實驗評分」另外使用英文全域順序配對，避開上游四段候選限制：行首兩詞必須在辨識輸出連續一致，全行至少一半詞一致，行起點必須來自有效且不倒退的原始詞時間。未匹配行保持空值，不依 SRT 或鄰近行補猜。此方法未取代原版對齊器；每次實驗保留當時歌詞快照，音檔、歌詞與人工參考相符時才顯示評分。

JS heap 不等於總 RAM 或顯示記憶體。GPU 與 Chrome 程序記憶體必須另行觀察；程序級數值也可能包含其他分頁。呼叫模型 `dispose()` 或中止 worker，不能視為已證明 driver 回收所有資源。

上游記憶體釋放及時間戳風險屬於本階段接受的限制。預設維持上游行為；可選時間對照依 [上游 PR #1809](https://github.com/huggingface/transformers.js/pull/1809) 的最後一列 prompt attention 語意實作，執行後恢復原方法，不是依 SRT 擬合固定偏移，也不代表已採用穩定修補。成功跑完與產生匹配結果皆不代表時間準確。

## 本機驗證結果

GTX 1050 Ti 4 GB、Chrome 155、WebGPU、上述固定模型 revision，輸入為更新後 206.68 秒的 Amazing Grace 完整混音，音檔 SHA-256 為 `138a911609554655a676e27499e532c23b2152e12f45d81f91acb0fef0ea04c1`。時間不含模型下載與音訊解碼。

| 設定 | 整首辨識耗時 | 輸出詞數 | 時間異常筆數 |
| --- | --- | --- | --- |
| tiny q4，含原生段落診斷 | 55.32 秒 | 522 | 764 |
| base q4，連續三次 | 42.76／41.30／35.59 秒 | 每次 389 | 每次 275 |
| base q4，額外保留原生段落 | 36.03 秒 | 389 | 275 |

一個詞可觸發多種異常，異常筆數可能超過詞數。額外解碼原生段落後，base 的全部詞級輸出與基準結果逐項相同。

改善實驗的記憶體採樣與摘要留在 `.local/results/improvement-memory.jsonl` 及 `improvement-memory-summary.json`。這些是程序級採樣，包含其他 Chrome 分頁，不是各模型的獨佔記憶體；5 秒採樣可能漏掉瞬間峰值，也不足以單獨定位上游洩漏原因。

本次 433 筆採樣中，Chrome GPU 程序專用記憶體峰值為 3222.2 MiB，全部 Chrome private bytes 峰值為 8213.5 MiB。候選完成後呼叫 `dispose()` 並終止 worker，最後樣本分別為 56.5 MiB 與 1028.2 MiB。採樣程序已停止；dev server 依使用者選擇保留運行。

使用者確認 SRT 為人工核對過的時間。19 個字幕段落可對應 17 個歌詞行起點；歌詞最後一行與前一行共用字幕，缺少獨立起點，排除評分。字幕與歌詞檔的部分文字不同，保留歌詞檔文字，以字幕時間作參考。此資料只有片語／行級時間，不能當作全部詞的真實時間。

base 預設停頓重建匹配 0／18 行；以原生段落轉接後，17 行可評分歌詞中匹配 1 行，起點誤差約 0.567 秒，其餘 16 行未匹配。原生段落共 19 個，沒有被排除的無效段落，1 個詞未能依起點歸入段落。

tiny 的預設停頓重建與原生段落轉接均為 0／17 行可評分歌詞匹配。零匹配的誤差統計為空值，不顯示成零誤差。

同一份 base 輸出的參數診斷最高匹配 10／18 行，其中 9 行可評分，但只有 3／17 行在一秒內，沒有行落在半秒內。已匹配行的絕對誤差中位數約 1.193 秒、P90 與最差值約 6.107 秒。這是單曲調參診斷，不是獨立驗證，設定未取代預設。

現階段已證明本機能完成整首 q4 辨識，尚未證明目前設定能提供可用的歌詞對齊品質。誤差統計僅包含已匹配行；成功率分母包含全部可評分行，未匹配不計作零誤差。

## 已驗證的改善候選

在同一 GTX 1050 Ti、Chrome、純瀏覽器、encoder／decoder 均為 q4 的限制下，最明確的文字改善來自將提供的歌詞放入 Whisper previous-text 提示區。這是已知歌詞情境，不是盲辨識基準；人工 SRT 未傳入推論或文字配對。

以下使用同一份 104 詞歌詞參考計算英文 WER。改善候選採英文全域順序配對，原始基準採原版對齊；「已匹配」不代表時間合格。

| 路徑 | WER | 可評分行中匹配 | ≤0.5 秒 | ≤1 秒 | 匹配行誤差中位數／P90 |
| --- | --- | --- | --- | --- | --- |
| base q4，原始設定與對齊 | 348.1% | 0／17 | 0 | 0 | 不適用 |
| base q4，歌詞提示＋順序配對 | 37.5% | 9／17 | 0 | 7 | 0.887／1.193 秒 |
| small q4，歌詞提示＋順序配對 | 28.8% | 11／17 | 0 | 6 | 0.987／1.507 秒 |
| small q4，另啟用時間修正 | 28.8% | 11／17 | 5 | 8 | 0.633／1.127 秒 |
| small.en q4，歌詞提示＋順序配對 | 15.4% | 14／17 | 0 | 5 | 1.080／1.507 秒 |
| small.en q4，另啟用時間修正 | 15.4% | 14／17 | 6 | 8 | 0.660／5.840 秒 |

文字主線候選為 small.en q4，30 秒切片、5 秒 stride、`max_new_tokens: 128`、不抑制 n-gram，使用提供的歌詞提示與原始時間，再做英文順序配對。固定 revision 見程式設定。時間修正雖讓部分行更接近人工參考，卻把 small.en 最差誤差由 2.193 秒擴大至 7.167 秒，因此不選為預設候選。small 的時間修正結果也仍有 7.167 秒的單一最差值；不能只看中位數或 P90 就認定整首可用。

此文字候選已重新建立模型重跑，兩次全部 106 個詞記錄（文字及起訖時間）逐項相同，均為 14／17 行匹配、5／17 行在一秒內；仍有 3 個零長度詞。兩次整首推論耗時為 46.55／76.30 秒，不含下載、模型載入與音訊解碼，這些是實測個案而非穩定效能保證。候選及重跑報告分別存於本機 `small-en-prompt-improvements.json`、`candidate-repeat.json`，最新彙整為 `summary.json`。

生成上限與重複抑制能減少循環，但 base 的 WER 仍達 84.6%；改成 15 秒切片後為 91.3%，沒有進一步改善。僅改大模型、未加歌詞提示時，small／small.en 分別為 74.0%／67.3%。這些是完整設定組合的比較，並非每一列都只改一個變因；base 的 `single128` 與 `single128-lyricprompt` 才是只新增提示的對照，WER 為 139.4% 與 37.5%。

CTC q4 強制對齊對所有 104 個提供詞分配了時間，但獨立辨識 WER 為 100%；只有 1／17 行在一秒內，行起點絕對誤差中位數為 13.817 秒，因此不採用這個模型／方法組合作候選。強制輸出正確歌詞文字不能替代聲學品質驗證。

目前支持的是「在本曲上有可量測改善」，尚未通過整首詞級品質驗收。small.en 原始時間候選仍有 3 個可評分行未匹配，其餘多數起點偏晚；本機 SRT 也只有行級起點，沒有每個詞的人工起訖。下一步驗收需要人工詞級標記及另一首未參與候選選擇的保留測試歌曲，不能用本曲的時間調參結果代替。

本機原始報告與最新彙整位於 `.local/results/`，公開 CLI 可重新核對音檔雜湊、歌詞、獨立辨識 WER 及行起點：

```sh
cd spike
node scripts/evaluate-experiments.ts ../.local/results/small-en-prompt-improvements.json ../.local/results/reference-map.json
```

## 問題分層診斷

目前證據支持辨識、詞級時間與段落轉接三層都有問題；尚無法把問題歸因於 q4 量化本身。所有比較維持 q4，沒有其他精度的對照組。

- **文字辨識：**忽略大小寫、標點與所有時間，以本機歌詞的 104 個英文詞計算 Levenshtein WER，base 詞級模式為 348.1%，tiny 為 491.3%；大量插入可使 WER 超過 100%。改用人工 SRT 文字作參考仍為 349.0%／493.3%。同批 token 改走原生段落解碼仍有大量錯字與重複，WER 為 365.4%／500.0%。因此無法靠換段落轉接消除文字問題。這是目前模型與生成設定在此混音上的結果，不能單獨證明量化精度是原因。
- **無時間戳對照：**base q4 在同一整首音檔、相同語言及 30／5 秒切片設定下，關閉時間戳的兩次輸出完全一致。輸出 36 個正規化英文詞，對歌詞及 SRT 文字的 WER 均為 89.4%（104 個參考詞，19 個替換、71 個刪除、3 個插入），沒有上述兩詞片語循環。文字路徑仍不可靠；時間戳模式的嚴重重複需與此問題分開分析。此對照會改變生成設定，並非只隱藏已生成的時間欄位。
- **原生段落時間戳對照：**base q4 設定 `return_timestamps: true`、`return_token_timestamps: false` 後，輸出仍有相同片語 145 次重複；正規化文字與先前詞級生成結果改走原生段落解碼完全一致，對歌詞的 WER 為 365.4%。因此本案例的循環在開啟時間戳的生成路徑即已出現，不必經過詞級時間擷取或本專案段落轉接。這個對照定位的是模式差異，尚未區分上游生成邏輯、模型能力、量化與此歌曲的交互影響；不能泛化成所有 q4 或所有歌曲皆會失敗。
- **合併前生成：**另一次 base q4 整首診斷保留了 10 個視窗，最終 389 個詞與既有輸出逐項相同。涵蓋音訊 80–110 秒的單一視窗，在重疊合併前就已把同一個兩詞片語生成 145 次；大量重複並非本專案段落轉接新增。原生段落與詞級模式的重疊合併規則不同，文字總量仍會不同，不能把兩者差異當成獨立模型辨識結果。
- **詞級時間：**base 有 261／389 個詞為零長度，tiny 為 401／522；另有負長度及起點倒序。以文字唯一且完全相同的三詞字幕開頭選取時間錨點，base 只有一個合格錨點，詞級起點比人工時間晚 0.973 秒；tiny 沒有合格錨點。因此目前不能估計全曲詞級時間誤差，也沒有證據支持只套用固定平移即可修好。
- **段落轉接與對齊：**固定同一份 base 詞與時間，只改實驗性分段／配對，匹配可由 0／18 變成 10／18，但仍只有 3／17 個可評分行在一秒內。人工 SRT 的文字與段落直接送入同一個對齊器，可匹配全部 17 個可評分行。合成控制也確認：正確段落前插入四個不相干段落，就會因上游四段候選視窗與失敗時游標不前進而完全失配。這是失敗的放大機制，不足以解釋模型生成的錯字與循環。

上述 WER 正規化僅供英文診斷；它與公開對齊器保留的原版大小寫／相似度行為不同。SRT 對照、合成控制及單曲參數比較均為定位實驗，不視為新的品質驗收結果。原始視窗與可重跑的診斷程式留於 `.local/`，未改預設演算法。

TypeScript 核心與原版 commit `ebe62d8a8628d0b2579987598f0442ebffcc68bb` 的 401 組字串相似度與 245 組對齊案例結果一致；對齊案例含 240 組合成資料及 5 組本機 segments。這是指定資料上的一致性檢查，不是所有輸入皆等價的證明。另有 19 項公開測試通過，涵蓋字幕解析、參考評分、更換音檔後防止沿用舊評分、CTC 路徑、英文順序配對與時間修正實驗的還原。原始歌曲報告、參考對應與記憶體採樣僅保留於 `.local/results/`。

